# DSG Design Ops Board

A small dashboard for the DSG Jira project. It shows:

- **Open tickets** and how many closed recently
- **Stale backlog** — tickets sitting untouched for a long time (default: 180 days)
- **Workload** — open tickets per person
- **Turnaround time** — how long tickets take from created to done
- **Status breakdown** — everything open, by status

It is a static site (no server needed to run it) plus one small Python script
that pulls the numbers from Jira. No frameworks, no build step.

```
dsg-dashboard/
├── docs/
│   ├── index.html        ← the dashboard page
│   ├── data.json         ← generated by the script (not committed — see below)
│   └── data.sample.json  ← placeholder data, shown until data.json exists
├── scripts/
│   └── fetch_data.py     ← pulls from Jira, writes docs/data.json
├── Dockerfile             ← nginx + python3, runs the fetch script then serves docs/
├── docker-entrypoint.sh
└── .env.example
```

`docs/data.json` is never committed to git — it's generated fresh inside the
running container (locally, or in Coolify) and only ever lives on disk there.
That also means the real ticket data never ends up in the GitHub repo, so the
repo's visibility (public/private) doesn't affect data privacy.

## 1. Run it locally first

You need a Jira API token (not your password):
<https://id.atlassian.com/manage-profile/security/api-tokens>

```bash
cp .env.example .env
# edit .env and paste your token in

export $(cat .env | xargs)      # loads the variables into your shell
python3 scripts/fetch_data.py   # writes docs/data.json
```

Then serve the `docs` folder and open it — most browsers block a page from
reading a local JSON file directly (`file://`), so a one-line local server is
needed just for previewing:

```bash
cd docs && python3 -m http.server 8000
# open http://localhost:8000 in your browser
```

No server is needed once it's actually hosted (GitHub Pages or Coolify serve
files over http, so the same `fetch('data.json')` call just works there).
Re-run the script any time you want fresh numbers.

If you skip this step, the page still works — it falls back to
`data.sample.json` so you can see the layout with made-up numbers.

## 2. Push it to GitHub

```bash
git init
git add .
git commit -m "DSG design ops board"
git remote add origin <your-repo-url>
git push -u origin master
```

This step is just to get the code somewhere Coolify can pull it from — no
GitHub secrets or Actions needed. Everything else (Jira credentials, the
refresh schedule) is configured in Coolify itself, next.

## 3. Host it on Coolify

A `Dockerfile` at the repo root is included — nginx serving `docs/`, plus
python3 so the same container can run `scripts/fetch_data.py`:

1. New Resource → your project → **Dockerfile** deployment, pointed at this
   repo/branch. Port: `80`.
2. Under **Environment Variables**, add `JIRA_BASE_URL`, `JIRA_EMAIL`,
   `JIRA_API_TOKEN`, `JIRA_PROJECT_KEY` (same names as `.env.example`) —
   enter these yourself directly in Coolify's UI.
3. Deploy. On container start, `docker-entrypoint.sh` runs the fetch script
   once (if `JIRA_API_TOKEN` is set) before starting nginx, so it goes live
   with real data already.
4. For ongoing refreshes without a full redeploy: in Coolify, go to this
   app's **Scheduled Tasks** and add a task running
   `python3 /app/scripts/fetch_data.py` on whatever cron schedule you want
   (e.g. weekday mornings). It writes straight into the running container's
   served folder — the next page load just picks it up, no rebuild needed.

If you'd rather match another app's existing Next.js setup instead of a plain
static site, say so and this can be restructured that way; this version is
deliberately framework-free so it's easy to run and review first.

## Adjusting the numbers

Two knobs live at the top of `scripts/fetch_data.py`:

- `STALE_DAYS` — how old a never-started ticket has to be to count as stale (default 180)
- `RECENT_DAYS` — the window used for "closed recently" and the turnaround-time average (default 90)

## Data privacy

`docs/data.json` is generated inside the container (locally or in Coolify)
and is gitignored — it's never committed, so the repo staying public doesn't
expose real ticket data. The dashboard *page* itself is public once deployed,
though (whoever has the URL can see live counts/names) — put it behind
Coolify's HTTP Basic Auth if that needs restricting.
